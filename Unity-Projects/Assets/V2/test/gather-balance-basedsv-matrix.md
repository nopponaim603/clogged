## 0. บทสรุปผู้บริหาร (อ่านแค่หัวข้อนี้ก็พอ)

1. **`baseSV = 50/30/10` ไม่ใช่ "เกมยากขึ้น" แต่เป็น "เกมพัง"** — เมื่อใช้กติกาเดิมทุกอย่าง (HS 1/2, Core 25/50)
   อัตราชนะของ Solo ตกลงจาก **86.65% → 4.62%** และชิ้นส่วน Core Item ต่อเกมเหลือ **1.814 → 0.287 ชิ้น**
2. **จุดพังไม่ใช่เส้นตรง แต่เป็น "หน้าผา" ที่ base Hard ระหว่าง 20 กับ 10** — เพราะ SV ของ Hard เดี่ยวถนัดคือ
   `base_H + 25` และทีมจะไม่ยอมออกทริปที่ SV ต่ำกว่า 40:
   `base_H = 20` → SV **45 ≥ 40 ผ่าน** (ทริป Hard ยังมี 58.9%)
   `base_H = 10` → SV **35 < 40 ตก** (ทริป Hard เหลือ 1.0%) → Hard หายไปจากเกม
   **เกณฑ์: base_H ต้อง ≥ 15** ไม่งั้นถ้ำ Hard ตาย
3. **มีอีกเส้นที่สำคัญกว่าที่หลายคนมองข้าม: Fumble** — `Roll()` ขยาย fumble จาก {100} เป็น {96–100} (1% → 5%)
   ทันทีที่ `SV < 50` การที่ Hard เดี่ยวถนัดมี SV = `base_H + 25` แปลว่า **base_H ต้อง ≥ 25** จึงจะยัง fumble 1%

## 1. วัตถุประสงค์ & ขอบเขต

รอบนี้ต้องการตอบ 4 คำถาม

1. ถ้าลด baseSV จาก `80/55/30` ลงมา **มีจุดที่ยังเล่นได้** ไหม หรือพังทันที
2. `70/45/25` กับ `65/40/20` ให้ผลต่างจากเดิมแค่ไหน และมี "เส้นตาย" เชิงกลไกที่ไหน
3. `Hard Success = 1/2` (ปัจจุบัน) เทียบ `1/3` ยังเป็นคันเร่งที่แรงกว่า core chance หรือไม่เมื่อ base เปลี่ยน
4. Core Item chance `25/50` เทียบ `5/15` ยังคุมความยาวเกมได้หรือไม่เมื่อ base เปลี่ยน

ตัวแปรที่ตรึงไว้ทั้งหมด (เหมือน V1 ทุกตัว): pity `Normal 3 / Hard 2`, เดดไลน์ 7 วัน, AP 3/วัน,
อาหารเริ่ม 8, cooking material 2, medicine 1, materials 0, aptitude bonus +25 (ครั้งเดียว),
duo +25, mismatch −10/ระดับ, trait ±10 (ครั้งละครั้ง), Blessed +10/คน, บุฟโพชั่น +10/ขวด (สะสมได้)

## 2. วิธีทดสอบ & ความถูกต้องของแบบจำลอง

### 2.1 แบบจำลอง

simulator เป็นคอนโซลแอป .NET แยกออกมา (ไม่ผูกกับ Unity) จำลองทีละวัน:

```
วัน → HealPhase → FoodPhase → DispatchPhase → EndDay(กินอาหาร/อด/ตัดสินแพ้ชนะ)
```

- **HealPhase**: รักษาคนเจ็บด้วยยา (1 AP) หรือไม่ใช้ยา (3 AP) — ถ้าคนรักษามี talent `Heal` ผู้ป่วยได้ `Blessed`
- **FoodPhase**: ถ้าอาหารไม่พอจะปรุง ใช้ cooking material + AP ของคนที่มี talent `Cooking` (ได้ ×2)
- **DispatchPhase**: สร้างทีม candidate ทั้ง Solo/Duo ไล่ทุกถ้ำ คำนวณ SV, กรองด้วยเพดานความเสี่ยง,
  ให้คะแนนด้วย expected Core Item ต่อ AP แล้วเลือกอันที่ดีที่สุด (รายละเอียดใน §3.3)
- **Core Item**: ทอย 1D100 เทียบ SV → Hard Success เท่านั้นที่มีสิทธิ์ดรอป
  `chance = base chance + 25` ถ้าทีมมี talent `Exploring` · pity นับเฉพาะ Hard Success ที่ไม่ได้ของ
  และเมื่อ pity ครบจะสุ่มชิ้นที่ยังขาด 1 ชิ้น (ไม่ใช่ทั้งสองชิ้น)

3 policy ที่ใช้ตัดสินพฤติกรรมผู้เล่น:

| policy | ความหมาย |
|---|---|
| **Solo** | ส่งเดี่ยวทุกทริป (ตัวที่ SV สูงสุดในถ้ำนั้น) |
| **Duo** | ส่งคู่ทุกทริป ถ้าส่งคู่ไม่ได้จึงส่งเดี่ยว |
| **Adaptive** | เลือกอิสระระหว่างเดี่ยว/คู่ โดยดู expected value ต่อ AP |

### 2.2 การตรวจสอบความถูกต้อง (ทำใหม่ทั้งชุด)

รันเทียบกับโค้ดจริงใน Unity (play mode, `GatherResolver` + `UnitManager` จริง) ได้ผล:

## 3. ข้อสังเกตเชิงกลไก (อ่านก่อนดูตาราง จะเข้าใจว่าทำไมตัวเลขออกมาแบบนี้)

### 3.1 เส้นตายสองเส้นที่กำหนดว่าถ้ำ Hard "มีอยู่จริง" หรือไม่

SV ของ **Hard เดี่ยว โดยคนที่ถนัด Hard (Boon/Dan)** = `base_H + 25` (โบนัสถนัด) + 0 (ไม่มี duo)

| base_H | SV | ผ่านเพดานเสี่ยง 40? | Fumble |
|---|---|---|---|
| 30 (ปัจจุบัน) | **55** | ผ่าน | 1% |
| 25 | **50** | ผ่าน | **1%** (50 ไม่นับว่า < 50) |
| 20 | **45** | ผ่าน (45 ≥ 40) | **5%** (ตกเกณฑ์) |
| 15 | **40** | ผ่านแบบเฉียดฉิว | 5% |
| 10 | **35** | **ไม่ผ่าน** | 5% |

จึงมีเส้นตาย 2 เส้นซ้อนกัน:

- **เส้นที่ 1 (ฟังก์ชันพัง): `base_H < 15`** → ทีมไม่ยอมไป Hard → ถ้ำ Hard ตายทั้งถ้ำ (seen ที่ S5–S8: hard trip 1.0%)
- **เส้นที่ 2 (ความรู้สึกพัง): `base_H < 25`** → Hard ทริปที่ "ควรจะปลอดภัย" กลายเป็นมี fumble 5%
  ผู้เล่นจะเริ่มรู้สึกว่า "เกมลงโทษฉันมากกว่าที่บอก" เพราะ SV 45 ยังดูสูงแต่จริง ๆ fumble ถี่ขึ้น 5 เท่า

`70/45/25` นั่งอยู่บนเส้นที่ 2 พอดี (SV 50) — เป็นเหตุผลว่าทำไมตัวเลขของ S13/S15 ยังดู "ปกติ"
ในขณะที่ S9–S12 (`65/40/20`, fumble 5%) เริ่ม cooks/run พุ่งเพราะทริปอาหารพลาดบ่อยขึ้น

### 3.2 โบนัสคงที่ไม่สเกลตาม base

SV = `base` + `+25` (ถนัด) + `+25` (คู่) − `10 × ระดับที่ห่าง` ต่อคน — โบนัสเป็นค่าคงที่ ไม่ได้ผูกกับ base

| สถานการณ์ | 80/55/30 | 70/45/25 | 65/40/20 | 50/30/10 |
|---|---|---|---|---|
| Duo ถนัดทั้งคู่ ลง Hard | 80 | 75 | 70 | 60 |
| เดี่ยวถนัด ลง Hard | 55 | 50 | 45 | **35** |
| เดี่ยวไม่ถนัด ลง Hard | 10 | 5 | **0** | **−10** |
| เดี่ยวไม่ถนัด ลง Normal | 45 | 35 | 30 | 20 |
| Easy ด้วย Boon/Dan (ห่าง 2 ระดับ) | 60 | 50 | 45 | 30 |

จุดที่ควรสังเกต: ที่ `65/40/20` มี **SV = 0** เกิดขึ้นจริง (Ann/Cia ลง Hard เดี่ยว) — ตัวเลข 0 บนการ์ดอ่านแล้ว
เหมือน "เกมพัง" มากกว่า "ยาก" และที่ `50/30/10` ก็มีค่าติดลบ ซึ่งควรถูก clamp หรือไม่ควรเกิดเลย

### 3.3 เพดานความเสี่ยง (SurvivalFloor) คือตัวเปลี่ยนเกม

บอท (และผู้เล่นที่มีเหตุผล) จะไม่เลือกทริปที่ SV ต่ำกว่า **40** เพราะ expected value ต่อ AP ต่ำมาก
ผลคือสัดส่วนทริปที่ไป Hard เปลี่ยนเป็นขั้นบันได:

| baseSV | hard trip% (Solo) |
|---|---|
| 80/55/30 | 55.3 |
| 70/45/25 | **67.3** |
| 65/40/20 | 58.9 |
| 50/30/10 | **1.0** |

ที่ `70/45/25` สัดส่วน **สูงกว่า** 80/55/30 เสียอีก (67.3% vs 55.3%) ทั้งที่ถ้ำ Hard ยากขึ้น — เพราะ Easy ที่ถูกลง
ทำให้ทริปหาของ/อาหารได้ผลตอบแทนต่อ AP น้อยลง (Cia ลง Easy เหลือ SV 60 จาก 70 → fail 29% → 39%)
ตัวให้คะแนนจึงหันไปลง Normal/Hard ที่ยังผ่านเพดาน 40 มากขึ้นแทน — สังเกตว่า trips/run แทบเท่าเดิม (8.31 vs 8.55)
แต่ cooks/run เพิ่มขึ้น 2.83 → 3.72 เพราะทริปอาหารพลาดบ่อยขึ้น นี่คือ "ต้นทุนแฝง" ของการลด base ที่ไม่โผล่ใน win%
แต่จะรู้สึกได้ในเกมจริงว่าต้องเสีย AP กับการปรุงอาหารมากขึ้น

## 7. ข้อสรุปและข้อเสนอแนะ

### 7.1 ตอบคำถามที่ตั้งไว้

**Q1: ลด baseSV ลงมาแล้วมีจุดที่ยังเล่นได้ไหม?**
มี แต่ต้องไม่ต่ำกว่า `70/45/25` — และ "จุดที่ยังเล่นได้" ไม่ได้เรียงเป็นเส้นตรง:

| baseSV | Solo win% | Δ จาก 80/55/30 | hard trip% | fumble ของ Hard เดี่ยวถนัด |
|---|---|---|---|---|
| 80/55/30 | 86.65 | — | 55.3 | 1% |
| **70/45/25** | **81.13** | **−5.52** | **67.3** | **1%** |
| 65/40/20 | 64.30 | −22.36 | 58.9 | 5% |
| 50/30/10 | 4.62 | −82.03 | **1.0** | 5% |

**Q2: 70/45/25 กับ 65/40/20 ต่างกันแค่ไหน?**
S13 กับ S9 ต่างกัน **17.2 pp** ที่กติกาเดียวกัน (1/2 · 25/50) และต่างกันมากขึ้นเมื่อ core chance ต่ำ
(S14 60.60 vs S10 39.58 = 21.0 pp) เพราะที่ base ต่ำ ทีมต้องเสีย AP ไปกับการปรุงอาหารเพิ่ม
(cooks/run 3.72 → 4.60) ซึ่งกิน AP ที่ควรใช้เดินถ้ำ — เป็น **ผลทวีคูณ** ไม่ใช่ผลบวก

**Q3: HS 1/2 กับ 1/3 ต่างกันแค่ไหน?**
ที่ base สูง: 86.65 → 70.21 (−16.4 pp) · ที่ `70/45/25`: 81.13 → 61.47 (−19.7 pp) ·
ที่ `65/40/20`: 64.30 → 46.80 (−17.5 pp)
→ **HS divisor แรงสม่ำเสมอ ~17–20 pp** ไม่ว่า base จะเป็นเท่าไร ต่างจาก core chance ที่แรงไม่สม่ำเสมอ

**Q4: core chance ยังคุมความยาวเกมได้ไหม?**
ได้ แต่ "ราคา" ต่างกันตาม base:

| baseSV | 25/50 median day | 5/15 median day | ราคาที่จ่าย (Δwin) | pity share ตอน 5/15 |
|---|---|---|---|---|
| 80/55/30 | 2 | 4 | −16.1 pp | 54.0% |
| 70/45/25 | 2 (81.13) | 4 (60.60) | −20.5 pp | 47.7% |
| 65/40/20 | 2 (64.30) | 4 (39.58) | −24.7 pp | 44.4% |
| 50/30/10 | 2 (4.62) | 3–4 (0.36) | −4.3 pp | 1.0% |

แถวล่างสุดคือหลักฐานว่า **เมื่อ base ต่ำ ตัวแปร core chance หมดความหมาย** เพราะไม่มี Hard Success ให้ pity ทำงาน

### 7.2 ข้อเสนอ (เรียงตามความเสี่ยงต่ำ → สูง)

1. **`70/45/25` + HS 1/2 + Core 25/50 (S13) — ตัวเลือกปลอดภัยที่สุดถ้าอยากขยับ base**
   81.13% win, median day 2, ชิ้นส่วน 1.741, และ **fumble ยัง 1% สำหรับตัวที่ถนัดถ้ำนั้น**
   (Ann-Easy 95 / Cia-Normal 70 / Boon-Dan-Hard 50 — ทั้งสามค่า ≥ 50 จึงไม่ตกช่วง fumble กว้าง)
   ส่วนตัวที่ไม่ถนัดจะตกเป็น 5% อยู่แล้วตามดีไซน์ของ mismatch penalty
   ข้อควรระวังเดียว: SV ของ Hard เดี่ยวถนัด = 50 **พอดีเส้น** ถ้าอนาคตลด base_H อีก 1 แต้มจะตกเกณฑ์ fumble ทันที
   → ควรใส่ comment ใน `GatherZoneDatabase` ว่า `Hard base ต้อง ≥ 25`
2. **`70/45/25` + HS 1/3 + Core 25/50 (S15) — ตัวเลือก "เกมยาวที่ยังยุติธรรม"**
   61.47% win, median day 3, HS rate 19.0%, pity share 9.1% → ยังเป็นเกม "ลุ้นดรอปจริง" ไม่ใช่ "รอ pity"
   ต้องแก้ `hardThreshold` เป็น `/3` ใน `GatherResolver.Roll` และในแถบเต๋าของ `DiceRollView`
3. **`65/40/20` (S9–S12) — ใช้ได้เฉพาะถ้ารับ cooks/run ที่เพิ่มขึ้น 60–190% ได้**
   ปัญหาหลักไม่ใช่ SV แต่เป็น **เศรษฐกิจอาหาร**: Easy ที่ 65 ทำให้ทริปหาอาหารของ Boon/Dan (ห่าง 2 ระดับ) เหลือ SV 45
   และ Cia (ถนัด Normal) เหลือ 55 → ทริปอาหารพลาดบ่อยขึ้น → ต้องปรุงเพิ่ม → AP หาย → เกมยืดแต่ไม่ได้ของ
4. **ห้ามใช้ `50/30/10` ในสถานะปัจจุบัน** — ไม่ใช่เพราะยาก แต่เพราะ **ทำให้ถ้ำ Hard ไม่ถูกเลือกเลย**
   และทำให้ SV ของ Hard ติดลบ (−10) ซึ่งบนการ์ดผู้เล่นจะเห็นตัวเลขติดลบ = bug ในสายตาเขา
5. **ถ้าจะปรับความยาวเกม ให้ปรับที่ HS divisor ก่อน** — เพราะผลสม่ำเสมอ (±17–20 pp ทุก base)
   และไม่แตะเศรษฐกิจอาหารเลย ต่างจาก base ที่ลามไปทุกอย่าง

### 7.3 สิ่งที่ควรทำต่อ

- **ใส่ guard ในโค้ด**: `GatherZoneConfig.baseSuccessValue` ของ Hard ควรถูก clamp ไม่ให้ต่ำกว่า 15
  (เส้นที่ทำให้ Hard ยังมีคนไป) และควรมี editor warning ถ้า `base_H < 25` (เส้น fumble)
- **ทดสอบ `70/45/25` ร่วมกับ talent `Exploring` (+25% core chance)** ซึ่งยังไม่ได้แยกทดสอบ —
  ที่ base ต่ำลง น้ำหนักของ +25% จะสูงขึ้นเมื่อเทียบกับ base chance
- **ทดสอบ HS divisor 1/4** เพื่อดูว่ายังรักษาความสัมพันธ์แบบเส้นตรง (~17–20 pp ต่อขั้น) หรือเริ่มไม่เป็นเส้นตรง
- **ทดสอบ base ที่ไม่เป็นขั้นเดียวกันทั้งสามถ้ำ** เช่น `70/45/25` แต่ Easy คงไว้ที่ 80
  (แยก "เศรษฐกิจอาหาร" ออกจาก "ความยากของถ้ำ" ได้ตรง ๆ)
