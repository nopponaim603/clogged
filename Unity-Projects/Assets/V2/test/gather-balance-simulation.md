**ข้อค้นพบหลัก 4 ข้อ**

1. **ลดอัตราดรอป กับ ลด Hard Success ให้ผลรวมพอ ๆ กัน (70%) แต่ให้ "ความรู้สึก" คนละแบบ** — S2 ทำให้ pity กลายเป็นแหล่งดรอปหลัก 54% (ผู้เล่นไม่ได้รู้สึกว่าทอยเก่ง แค่รอครบ) ส่วน S3 ทำให้ pity แทบไม่มีบทบาท (10.9%) และของยังมีค่าอยู่
2. **สองปุ่มนี้ทำงานแยกกันจริง (orthogonal)** — HS rate ขึ้นกับตัวหารอย่างเดียว (÷2 → ~30.2%, ÷3 → ~20.3% ไม่ว่าจะตั้ง rate เท่าไร) และอัตราดรอปขึ้นกับ `coreItemChancePercent` อย่างเดียว การจูนจึงเลือกได้อิสระ
3. **กดทั้งสองปุ่มพร้อมกัน (S4) แรงเกินไป** — win เหลือ 43.5% และตกรอบเพราะหมดเวลา 53.7% ไม่ควรใช้คู่กัน
4. **ส่งคู่ (Duo) เป็นตัวเลือก "เชิงรับ" ที่ยังไม่คุ้ม** — ตายหมดทีม 0.00% ทุกกติกา (Solo 2.5–2.8%) แต่แพ้% มากกว่าเมื่อ pity ต่ำ (S2 −9.3pp, S4 −6.8pp) เพราะทริปน้อยลง → pity เดินช้า

**ข้อเสนอ:** ใช้ **S3 (HS ≤ SV÷3 · Core 25/50)** เป็นฐาน แล้วปรับ `coreItemChancePercent` ลงเล็กน้อย (เช่น 20/40) หากยังรู้สึกว่าเร็ว — หรือกลับไปใช้ **÷2 + pity 4/3 + rate 10/25** (ค่า B2 ที่ทดลองไว้ในรายงานฉบับก่อน) หากต้องการคง HS ให้ออกบ่อย

### 2.3 ผลกระทบเชิงทฤษฎีของแต่ละตัวแปร (คำนวณมือ ก่อนทดลอง)

**ตัวแปร A — ตัวหาร Hard Success (÷2 → ÷3)**

ช่วง Hard Success = ทอย `1 … ⌊SV/D⌋` (หลังหัก Fumble แล้ว) ดังนั้น

$$
P(\text{HS}) = \frac{\lfloor SV/D \rfloor}{100}, \qquad D \in \{2, 3\}
$$

การเปลี่ยน D จาก 2 → 3 ทำให้ **ช่วง HS แคบลงเหลือ 2/3** แต่ยอดผู้เล่นที่ "สำเร็จ" (HS + Regular) **ไม่เปลี่ยน** เพราะ Regular ขยายมากินช่วงที่หายไป:

$$
P(\text{สำเร็จ}) = \frac{\min(SV,\,99)}{100} \quad \text{(เท่าเดิมทุก D)}
$$

⇒ **÷3 ไม่ได้ทำให้เกมยากขึ้น แต่ทำให้ "คริติคอล" หายากขึ้น 1/3** → จำนวนครั้งที่ได้ทอย Core Item ลดลง 1/3

**ตัวแปร B — `coreItemChancePercent` (25/50 → 5/15)**

ของจะดรอปก็ต่อเมื่อ **Hard Success + ทอยผ่าน** ดังนั้นอัตราดรอปต่อทริปคือ

$$
P(\text{ได้ชิ้น}) \approx P(\text{HS}) \times \frac{c}{100} \times (\text{จำนวนชิ้นที่ยังขาด})
$$

| | Normal | Hard |
|---|---|---|
| c เดิม | 25% | 50% |
| c ใหม่ | 5% | 15% |
| อัตราส่วน | **÷5** | **÷3.3** |

⇒ Normal แพ้ผลหนักกว่า Hard มาก (5 เท่า vs 3.3 เท่า) — **การลด rate ทำให้ Hard กลายเป็นถ้ำที่คุ้มกว่าอย่างชัดเจน** ซึ่งเป็นการเปลี่ยน "จุดสนใจของเกม" ไม่ใช่แค่ความยาก

**ตัวแปร B มีเพดานล่างจาก pity** — เพราะ pity การันตีชิ้นหนึ่งทุก ๆ `p` ครั้งที่ HS ติดกันโดยไม่ดรอป ดังนั้นต่อให้ `c = 0` ผู้เล่นยังได้ชิ้นหนึ่งทุก ~`p` HS:

$$
\text{ชิ้นต่อ HS} \ge \frac{1}{p}
$$

| โซน | p | เพดานล่าง (ชิ้น/HS) |
|---|---|---|
| Normal | 3 | 0.333 |
| Hard | 2 | 0.500 |

⇒ **นี่คือเหตุผลที่ S2/S4 ยังมีชิ้น/HS ถึง 0.36–0.39** ทั้งที่ rate ลดลง 5 เท่า — pity คือกลไกที่ "กันไม่ให้แย่กว่านี้"

## 3. ระเบียบวิธีทดสอบ

### 3.1 แบบจำลอง

เขียน simulator แยกต่างหาก (**ไม่แตะโค้ดเกม**) เลียนแบบลูปเกมจริงทีละขั้น:

```
for day = 1..7:
    HealPhase()      # รักษาคน Hurt ด้วยยาถ้ามี ไม่งั้น 3 AP
    FoodPhase()      # ถ้า Food < จำนวนคนที่ยังมีชีวิต → Cook ก่อน ถ้า CM หมด → ไป Easy
    DispatchPhase()  # เลือก (ทีม, ถ้ำ) ที่ให้ expected Core Item ต่อ AP สูงสุด แล้วยิง
    EndDay()         # กินอาหาร 1/คน · คนไม่พอได้ +1 starve (ครบ 3 = Missing)
    if มี Core ครบ A+B → ชนะทันที
    if day > 7 → แพ้ (deadline)
    if ทุกคนตาย → แพ้ (all-lost)
```

### 3.2 การตรวจสอบความถูกต้อง (สำคัญ — ทำก่อนเชื่อตัวเลข)

| สิ่งที่ตรวจ | วิธี | ผล |
|---|---|---|
| สูตร SV | เทียบกับ `GatherResolver.ComputeSuccessValue()` ใน Unity Runtime **ทั้ง 30 combo** (10 ทีม × 3 ถ้ำ) | **ตรงกัน 30/30** |
| การแบ่งระดับผล | เทียบกับ `GatherResolver.Roll()` ยิงจริง **200,000 ครั้ง/ค่า** ที่ SV = 10, 45, 55, 80, 105 | ต่างกัน ≤ **0.2pp** (เช่น SV 45: แบบจำลอง 22.0% vs เกมจริง 22.0%) |
| ช่วง Fumble | ตรวจสูตร `SV<50 → 96–100` / `SV≥50 → 100` ตรงกับโค้ด | ตรง |
| ค่า zone | `GatherZoneDatabase` default (80/55/30 · AP 1/2/3 · pity 3/2) | ตรง |

ทั้ง 3 policy ใช้ AI ตัวเดียวกันในการเลือกถ้ำ (สูงสุดตาม expected Core Item ต่อ AP) และมีเงื่อนไข "ไม่ส่งถ้ำที่ SV < 40" เพื่อกันการฆ่าตัวตาย (สุ่มเสียคนเปล่า ๆ)

### 3.6 ข้อจำกัดที่ต้องระบุ

1. **AI เล่นดีเกินคนจริง** — รู้ pity counter ล่วงหน้าและจัดทีมเป๊ะทุกวัน ตัวเลข win% จึงเป็น **เพดานบน** ผู้เล่นจริงน่าจะต่ำกว่านี้ 10–25pp
2. **ไม่ใช้ Buff Potion / ไม่คราฟยา** — ถ้าใช้จะยิ่งเร็วขึ้น (Buff Potion +10 SV ต่อ stack) ⇒ ตัวเลข S1 ที่เร็วอยู่แล้วจะเร็วกว่านี้อีก
3. **ไม่มีการตัดสินใจเชิงกลยุทธ์** เช่น "เก็บ AP ไว้พรุ่งนี้" หรือ "ยอมไม่กินอาหารเพื่อประหยัด" — AI ใช้ AP ให้หมดทุกวัน
4. **Materials ไม่ถูกใช้** — ตัวเลข Materials ที่ได้จึงไม่มีความหมายในรายงานนี้
5. **ไม่จำลองการรีสตาร์ท/โหลดเซฟ** — 1 run = 1 ชีวิต ไม่มีการ savescum

3. **S2/S4 ช้าเกินไปและ "ผิดธรรมชาติ"** — pity แบก 54%/46% ของของที่ได้ แปลว่าผู้เล่นส่วนใหญ่ได้ของเพราะ **"ครบเงื่อนไขการันตี"** ไม่ใช่เพราะทอยเก่ง ⇒ ตัวเลข `coreItemChancePercent` แทบไม่มีความหมายต่อความรู้สึกของผู้เล่น (มันกลายเป็นแค่ตัวนับถอยหลัง)
4. **มี "หน้าผา" ที่ Normal** — เพราะ `c` ลดจาก 25→5 คือ **÷5** แต่ Hard ลดแค่ **÷3.3** ⇒ S2/S4 ทำให้ถ้ำ Normal **แย่ลงอย่าง disproportionate** และบีบให้ผู้เล่นต้องไป Hard อย่างเดียว ซึ่งขัดกับเจตนา "Easy → Normal → Hard" ที่เป็นบันได

**สาเหตุเชิงตัวเลข (ยืนยันจาก §2.3):** เมื่อ pity มีเพดานล่างที่ `1/p` ชิ้น/HS การลด `c` ลงมาก ๆ จะทำให้ผลลัพธ์ **ลู่เข้าค่า pity** ไม่ใช่ค่า `c`:

| โซน | p | เพดานล่าง | ค่าที่วัดได้ S1 | ค่าที่วัดได้ S2 |
|---|---|---|---|---|
| Normal | 3 | 0.333 | — | ← เข้าใกล้ค่านี้ |
| Hard | 2 | 0.500 | — | ← เข้าใกล้ค่านี้ |
| รวม (ผสม) | — | 0.36–0.39 | — | **0.392** ✔ |

⇒ ที่ S2/S4 ระบบอยู่ในสภาวะ **"pity-driven"** ไม่ใช่ **"luck-driven"** อีกต่อไป

### 6.3 เกมจบเร็วไปไหม (ตอบ Q3)

| # | win% | median | ชนะ d1 | ชนะ d3 | ชนะ d5 | deadline% | all-lost% |
|---|---|---|---|---|---|---|---|
| **S1** | 86.65% | **2** | **27.0%** | 62.4% | 78.6% | 10.8% | 2.54% |
| **S2** | 70.55% | 4 | 6.1% | 31.1% | 54.3% | 26.8% | 2.69% |
| **S3** | 70.21% | **3** | 17.8% | 44.2% | 59.8% | 27.2% | 2.60% |
| **S4** | 43.50% | 4 | 3.8% | 15.6% | 29.8% | **53.7%** | 2.77% |

**ข้อสรุป Q3**

- **S1: เร็วเกินไป** — median วันที่ 2 และ **27% ชนะตั้งแต่วันที่ 1** คือมีคนจำนวนมากที่ "ไม่เคยเห็นวันที่ 2" ⇒ ทั้งระบบ heal/cook/starvation/AP ถูกข้ามไปโดยสิ้นเชิง กรอบ 7 วันถูกใช้จริงแค่ ~2.7 วัน
- **S2 กับ S3 ให้ win% เกือบเท่ากัน (70.6 vs 70.2) แต่ "ความรู้สึก" ต่างกัน** — S3 จบไวและมีช่วงหัวเกมที่ได้ของ (17.8% ชนะ d1) ส่วน S2 เนือย (6.1% d1, median 4) ⇒ **S3 สนุกกว่าในช่วงต้นเกม** เพราะผู้เล่นได้ feedback เร็วกว่า
- **S4: โหดเกินรับ** — ตกรอบเพราะหมดเวลา **53.7%** คือเกินครึ่งของผู้เล่นจบเกมด้วย "ความล้มเหลวจากนาฬิกา" ซึ่งไม่ใช่ความล้มเหลวที่ผู้เล่นควบคุมได้
- **all-lost ~2.6% ทุกกติกา** — ไม่ผันผวนตามกติกา เพราะเกิดจาก starvation ไม่ใช่จาก Fumble ⇒ **ระบบอาหารคือกลไกตายหลัก ไม่ใช่ Core Item** (น่าสนใจ: ตัวเลขนี้แทบไม่ขยับเลยทั้ง 4 กติกา)

**ข้อสรุป Q4**

2. **ΔDuo เป็นลบมากขึ้นเมื่อ `c` ต่ำ** (S1 +0.35 → S2 −9.32) ⇒ **ยิ่งดรอปยาก duo ยิ่งแย่** เพราะ pity ต้องใช้ "จำนวนครั้ง HS" ซึ่ง duo ทำได้ช้ากว่า
3. **Duo เป็น "ประกันชีวิต" ที่ได้ผลจริง** — all-lost **0.00%** ทุกกติกา (Solo 2.5–2.8%) เพราะไม่เหลือ people ว่างให้ starvation กิน ⇒ **duo ควรถูกออกแบบให้เป็นตัวเลือกเชิงรับ ไม่ใช่เชิงรุก**
4. **Adaptive ≈ Solo เกือบทุกช่อง** (ต่าง ≤ 0.4pp) ⇒ AI มองว่า "คู่ไม่คุ้ม" ภายใต้กติกาปัจจุบัน นี่คือสัญญาณว่า **duo bonus +25 อาจน้อยเกินไป** ถ้าอยากให้ผู้เล่นเลือกคู่จริง ๆ

- ตัวชี้วัด HS rate แม่นที่สุด (SD ≤ 0.20pp) เพราะเป็นสัดส่วนของเหตุการณ์ที่เกิดถี่

**ถ้าเลือกทาง A/B ควรทำเพิ่ม 3 อย่าง**

1. **ชดเชย Duo** — เพิ่ม `DuoBonus` จาก 25 → 35 หรือให้ duo ได้ HS roll 2 ครั้ง (advantage) เพื่อให้ HS/run ของ duo อย่างน้อยเท่า solo
2. **ปรับถ้ำ Normal ไม่ให้เป็นหลุม** — ถ้าลด rate ให้ลดแบบสัดส่วนเดียวกัน (25→20, 50→40) อย่าลด Normal 5 เท่าแต่ Hard 3.3 เท่า
3. **ทบทวนกรอบ 7 วัน** — เมื่อ median อยู่ที่วันที่ 3 กรอบ 7 วันทำให้ 30% ของ run "เนือยช่วงท้าย" พิจารณาลดเหลือ 5 วัน หรือเพิ่มเงื่อนไขกดดันช่วงท้าย (เช่น อาหารลดลงทุกวัน)

**สิ่งที่ *ไม่* ควรทำ**

- ❌ ใช้ S4 (กดทั้งสองปุ่ม) — เกินไป 43.5%
- ❌ ลด `c` โดยไม่แตะ pity — จะทำให้ระบบเป็น pity-driven (S2 = 54%) และผู้เล่นหมดความรู้สึกว่าทอยเก่ง
- ❌ เพิ่ม Fumble penalty เพื่อถ่วงเกม — all-lost มาจาก starvation อยู่แล้ว (2.6% คงที่ทุกกติกา) การเพิ่ม Fumble จะซ้ำเติมผิดที่

## 8. อภิธานศัพท์

| คำ | ความหมาย |
|---|---|
| **HS** | Hard Success — ทอย ≤ ⌊SV ÷ ตัวหาร⌋ |
| **SV** | Success Value — ค่าโอกาสสำเร็จที่คำนวณจากถ้ำ + ทีม (§4.3) |
| **pity** | ระบบการันตี — HS ติดกัน `p` ครั้งโดยไม่ดรอป → ครั้งถัดไปการันตี 1 ชิ้น |
| **pity share** | สัดส่วนของ Core Item ที่ได้มาจากการันตี (ไม่ใช่จาก `coreItemChancePercent`) |
| **Solo / Duo / Adaptive** | policy การส่งยูนิต (เดี่ยวเท่านั้น / คู่เมื่อทำได้ / เลือกที่คุ้มที่สุด) |
| **paired seed** | ใช้ชุดเลขสุ่มเดียวกันทุก scenario เพื่อให้เทียบผลได้ตรง |
| **all-lost** | แพ้เพราะยูนิตหายหมด (ในทางปฏิบัติมาจาก starvation) |
| **deadline** | แพ้เพราะครบ 7 วันแล้วยังไม่มี Core Item ครบ |
| **pity-driven** | สภาวะที่ของส่วนใหญ่มาจากการันตี จน `c` แทบไม่มีผล |
